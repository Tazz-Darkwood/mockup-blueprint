# Create a new mockup with context

The job when the user wants a new mockup. Read `SKILL.md` first.

**What to read, and when.** There is a lot, and not all of it is needed before the first line is drawn.

| Before | Read |
|---|---|
| the brief (step 4) | `library/style-guide.md`: how the stack works, "Write a design brief", "Decide where the detail goes", "It must not look like a template". Then each guide chosen, all of it, and for every feel guide after the first, its "When this guide is not the lead", with "When guides are stacked" in the general guide. |
| writing HTML (step 5) | `library/style-mobile.md` from "Use it properly" to the end of "Before showing a mockup". "Use it properly" and the note titles of each tool's entry, `library/web-platform.md` and `library/css-layout.md`; open a note when its title matches what you are about to write. |
| writing the context (step 10) | `references/context-format.md`, then `references/gap-checklist.md`. |

The rest of the general style guide's notes are a reference for the "Before showing a mockup" list in step 6: read them there.

1. **Get the intent first.** Before drawing anything, find out: what it is for, who uses it, the handful of things they must be able to do, what data is involved, whether there are existing brand colours or references, and which tools it should be built with. Ask; do not invent a product.
   - Unless they name tools, the default for a small site (one to a few pages, nothing saved on a server) is plain HTML, CSS and a little script, opened by double-click, with its fonts kept in its own folder. Say so as a suggestion; it changes only if the site needs a server.
   - Offer a suggested answer with each question, as the Annotate job does. Someone who is not a web person gets little from "what data is involved?" and a great deal from "nothing saved: is that right?". When the request is a sentence and the content is itself what is to be made (a joke site, a game), the suggestions will carry most of the ideas. Every one of them is a proposal until the user says yes, and is written down as one.
   - If they want it to look like someone else's work (a game, a film, a brand), or to use its logo, art or names, read "When the look belongs to someone else" in `references/jobs/style-guide.md` before going on: capture the feel, use none of the property, and say so plainly if they ask for the property itself.
   - Steps 1, 3 and 4 each end in asking. For a small request they may go to the user in one message: the questions, the guides, and a brief written on the suggested answers. Head that brief "Proposal" and say it rests on answers not yet given. Rewrite it once they are.

2. **Read what applies, at the time the table above gives.** Now: the library entry for each tool the user named, enough to know what it can do, and `library/style-guide.md` on how the style stack works (the general guide, the purpose, feel and field guides a site stacks on it, and the site's own guide). The phone guide and the tool notes on HTML and layout wait until the brief is agreed, as the table says. If a tool the user named has no library entry, say so: its behaviour is unverified, so try what matters with `try` as you go, and propose notes for what surprises you.

3. **Choose the look with the user.** Run `style` to list the recipes, the parts and the guides there are, the skill's and the ones the user has made.
   - **Personality first:** serious, calm, friendly, playful or dramatic, one word for the whole site. It decides which picks agree.
   - **Then a recipe, or parts.** A recipe is a whole look as part picks (`style-recipe-*.md`). If one fits, offer it, and say which parts the user might change ("the field journal, but at dusk"). If none fits, build the look from parts: for each part, a starting point or layer picks, shown in its swatch book in `library/tests/parts/` so the owner can choose by looking. Read each option before using it: its "Made with" and "Careful" lines are what worked on earlier mockups. Where two parts reach for the same thing, the owner in "Parts, layers and the shared colour names" in the general guide wins. A look built from parts that the owner likes becomes a new recipe in their styles folder ("Recipes" in the general guide), with the two to four things made for it written under "What makes it".
   - When the owner likes one thing from a look but not the rest ("that background, but not that whole look"), change that one part or one layer, not the whole look.
   - **Purpose and field guides still stack on top** (sales, education): they arrange what the page must do and what that trade's visitors expect, not how it looks. Name them in `project.style.guides`. The feel guides (warm, artistic, professional) are being replaced by recipes of the same names; use the recipe. If a feel guide is stacked with others, the first sets the page's colour, its top and its main material ("When guides are stacked" in the general guide), and the site guide records how they met.
   - If the user wants a look from somewhere else (a kind of art, a game, a period), build it from parts first; research it online only when the parts cannot hold it (`references/jobs/style-guide.md`).
   - Record the choice in the site guide now, and in the blueprint as `project.style` once `init` has made the blueprint at step 5: `{"personality": "friendly", "recipe": "field-journal", "parts": {"light": {"sky": "dusk"}}, "guides": ["sales"], "site_guide": "name.style.md"}`. Leave out what is not used.

4. **Write the design brief and show it before drawing.** It is the eight lines the general style guide asks for. Agreeing it first is far cheaper than redrawing a mockup whose tone was wrong. The brief is the first section of the site's own guide, `<name>.style.md`, kept beside the mockup; `references/site-guide.md` lists that file's sections. Start the file now and fill the rest in as the page is drawn.
   - If the site has no name yet, give the folder a plain working name that says what it is (`bakery-quiz`), call the page `index.html` and the site guide after the folder, and say in the brief that the name is a working one. Do not rename files when the real name arrives: the name goes into the pages, the brief and `project.name`, and the folder may be renamed as a whole if the user wants.

5. **Build the mockup with anchors from the start, phone first.** Run `init` as soon as the first page exists, so `audit`, `check` and `try` work from then on; the context file starts empty and is filled in at step 10.
   - **Start the styles from the picks.** Once `init` has made the blueprint and `project.style` holds the recipe or parts, run `style css <folder>`. It writes `parts.css` (every picked option's code, in the owners' order, with the recipe's tuned values), `parts.js` (the SVG pieces and scripts the picks use) and copies the fonts with their licences. Link `parts.css` before the site's own stylesheet and load `parts.js` with `defer`; build the page from the hooks it styles (`.page`, `.band`, `.sheet`, `.panel`, `.btn`, `.btn-main`, `.field`, `.tag`, `.badge`, `.picture`, `.deco`), and add the markup it lists under MARKUP. Then put the site's own things, the recipe's "What makes it", in the site's stylesheet: the picks set the parts, not the look's signature. Changing a pick means running `style css` again, so keep site changes out of `parts.css`.
   - Choose this site's typefaces and colours for its own subject. Do not copy the fonts or tokens of another mockup that happens to be in the next folder.
   - Set the style guide's tokens first (type scale, spacing scale, colours, radius) and use only those.
   - Lay the page out at phone width before anything else: one column, in the order a visitor needs things, with the first screen decided on purpose, as `library/style-mobile.md` describes. Widen it afterwards and add columns only where the content gains from them. A page drawn wide and squeezed later puts the wrong things first on a phone, and most visitors to most sites are on one.
   - Put `data-bp-screen` and `data-bp` on elements as you write them.
   - Make it accessible by construction: real `<button>`, `<a>`, `<label>` and heading elements, a `lang` attribute, a title, alt text, visible focus, text contrast of at least 4.5:1. It is far cheaper than retrofitting.

6. **Before the user sees anything**, run the "Before showing a mockup" list of every guide in the stack (the general guide and the phone guide have one; a feel, purpose or field guide keeps its checks in the last steps of its "Use it properly"), and `audit`. The last item on the general list is the template test: count the template tells and name three things on the page that were made for this site alone. It is the one check no script can do for you and the one users notice first, so do not skip it because everything else passed.
   - The general list asks to compare the page with the last mockup made. That is the most recently changed folder beside this one that holds a mockup of a different site; other versions of this same site (a copy, an attempt the owner turned down) do not count. Look at it side by side to catch a look carried over by habit; take nothing from it.

7. **Show the look, then wait for the user's reaction.** Give them pictures of the page (`try page.html --shot first.png`, `--strips` for a long page, `--phone` for a phone) and say how to open it. Ask what is wrong with the look, in their own words. Do not write the context first (if nobody can be asked, the context so far holds only `project.name`, `project.style` and the questions that record your defaults): people criticise how a page looks before anything else, and context written for a page that is then redrawn is written twice. Fix what they say, as SKILL.md describes for criticism and `references/jobs/revise.md` sets out, and show it again until they are content with the look. Then go on.

8. **Click through it as each kind of user.** Before writing any context, open the mockup and use it as a visitor, as a signed-in member, and as any other role, at desktop and phone width. The audit checks the markup; only using the page shows that something a role should see is missing or that a button leads nowhere. `try page.html "click #x" "fill #y=text"` carries out a few presses and reports errors, messages and where the focus went.

9. **Show the states that matter.** Where it is cheap, mock the empty, loading and error states too, or describe them in the element's `states`. The check only sees a page as it loads, so list the presses that reach each other state (a form that opens, a message after sending, a full list) in `project.check_states`; the check then looks at those as well.

10. **Write the context**, the same way as steps 4 to 9 of `references/jobs/annotate.md`. Then report as its step 9 says; the user has already seen the look, so the report is about what the page does and the questions still open.
   - For a mockup of several pages, pass every page to one `init` command so they share one context file (run it again when a page is added), and give the shared parts (header, footer) the same `data-bp` id on every page so they are described once.
   - If the pages share anything that changes (who is signed in, a basket, a game), the browser's storage alone will not carry it from page to page: opened from a folder, some browsers keep separate storage for every file, so one page cannot read what another saved and the mockup seems to forget things. Copy `assets/carry-storage.js` beside the pages and load it first on every one; the pages then use `localStorage` as usual. Where a script sends the visitor to another page, use `carryStorage.go('page.html')`, not `location.href`. `audit` and `check` try this for every mockup of more than one page and report `mockup/storage-not-shared` or `mockup/script-leaves-storage`.
   - If the mockup needs a control that only exists to show different states, such as a "view as visitor or member" switch, mark it `mock_only`.
   - Everything the user told you is confirmed. Everything you chose to make the mockup look complete (sample names, numbers, extra menu items) is inferred or `mock_only`. Say which is which, because invented filler is the most common thing to get built by accident.
